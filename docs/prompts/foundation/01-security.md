# برومبت 01 — معالجة موانع الأمان العاجلة

جاهز للنسخ بالكامل. يتضمن العقد العام؛ لا تحتاج إلى نسخه من ملف آخر. هذا طلب تنفيذ مستقبلي وليس إثبات إكمال.

```text
أنت وكيل هندسة منتج يعمل على مستودع jira-nexus الحالي. نفذ الخطوة المحددة بعد هذا العقد فقط.

السياق:
- اقرأ AI_DEVELOPMENT_RULES.md وdocs/SYSTEM_REVIEW_AR_2026-10-20.md وخطة التنفيذ وبرومبت الخطوة.
- افحص git status والتغييرات الموجودة. لا تمسح عمل المستخدم ولا تستبدل قاعدة بياناته ولا تعيد seed لها.
- داخل جلسة Arena الحالية اعمل على arena/bbfbb187-jira-nexus فقط؛ لا تنشئ أو تبدل فروعاً، ولا commit/push/PR إلا بطلب. إذا اختلف السياق لاحقاً توقف لتأكيد الفرع.
- لا تفترض أن README يصف التشغيل الحالي. تتبع package scripts ونقطة الدخول والواجهة وقاعدة البيانات وملفات النشر.
- تحقق من اعتماديات الخطوة في الخطة. إذا لم تتحقق، وضح العائق وتوقف عن التغييرات المعتمدة عليها؛ لا تصطنع اكتمالها.

قبل التنفيذ:
1. اعرض جرداً مختصراً: الموجود، الجزئي، الناقص، والأدلة بمسارات الملفات.
2. اعرض النطاق والملفات والعقود وترحيلات البيانات والمخاطر وخطة الاختبار والتراجع.
3. قسّم المهمة الكبيرة إلى أجزاء قابلة للمراجعة. لا تدّعِ تنفيذ أجزاء لم تنجزها.

ضوابط التنفيذ:
- أعد استخدام الوحدات الصحيحة؛ لا تنشئ مساراً موازياً أو framework جديداً أو تعيد كتابة التطبيق دون ADR مبرر.
- التزم بوحدات المجال وفصل HTTP عن قواعد العمل والتخزين. أضف DTO والتحقق من المدخلات وأخطاء واضحة.
- تحقق من الهوية والمستأجر والصلاحية على الخادم لكل مورد وعملية، بما فيها البحث والملفات وjobs والأحداث والتصدير.
- لا تستخدم نجاحاً وهمياً عند فشل API، ولا mock إنتاجياً، ولا secret أو بيانات شخصية في السجلات.
- لا تقرأ أو تطبع أو تنسخ أسراراً في الرد. استخدم placeholders في الأمثلة، ومتغيرات بيئة ومخزن أسرار.
- لا تنفذ تدوير اعتماد خارجي أو ترحيل إنتاج أو حذف تاريخ Git أو نشر أو اتصالاً مدفوعاً دون تفويض منفصل.
- migrations مرقمة مع اختبار من قاعدة جديدة ومن الحالة السابقة؛ اختبر على بيانات اصطناعية أو نسخة مأذونة ومعزولة.
- للعمليات الحساسة عالج التزامن وidempotency وحدود الاستخدام. لا تعد بـexactly-once عبر أنظمة خارجية.
- واجهات جديدة قابلة للترجمة وRTL والوصول، مع loading/empty/error/retry. احترم عقود الميزات القديمة المعتمدة.
- اكتب اختبارات happy/failure/edge cases والصلاحيات والعزل عند انطباقها؛ لا تحذف اختباراً فاشلاً أو تضعف تأكيداته لتمريره دون تفسير تغيير العقد.
- عند تشغيل preview اربط 0.0.0.0 واستخدم /api نسبيّاً مع proxy؛ لا تجعل متصفح المستخدم يتصل بـlocalhost لخادم آخر.

التسليم:
- ملخص التغييرات والملفات، أوامر التحقق ونتائجها الفعلية، وأي اختبار لم يعمل وسببه.
- تحديث docs/execution/step-NN.md: معايير القبول كل منها pass/fail/blocked ودليله، القرارات، المخاطر، الترحيل والتراجع والخطوة التالية.
- اعرض git diff --check وراجع الفرق بحثاً عن الأسرار والتغييرات غير المقصودة.
- لا تقل «جاهز للإنتاج» أو «متوافق بالكامل» أو «آمن تماماً» اعتماداً على نجاح البناء وحده.

المهمة المحددة — 01:
نفذ الخطوة 01: تأمين الوضع الحالي قبل التوسع.
افحص render.yaml ومسار api/index.js → app.js → auth.js والصلاحيات في web/src/api.js، وتحقق من المسار الجديد أيضاً.
أزل الأسرار الصريحة من ملفات الإعداد لصالح مراجع آمنة، وأضف مثال إعداد بلا قيم حقيقية وفحص أسرار لا يعرض القيم. لا تغيّر تاريخ Git أو تستخدم بيانات الاتصال.
أزل fallback الذي يربط مستخدماً مفقوداً بهوية أخرى، وأوقف قبول جلسة ملغاة بإعادة إنشائها من التوقيع. امنع الأسرار الافتراضية في الإنتاج، مع فشل إقلاع واضح.
اجعل فشل حفظ/قراءة الصلاحيات ظاهراً وآمناً بدلاً من اختلاق نجاح أو صلاحيات واسعة.
اختبر: مستخدم غير موجود، جلسة ملغاة/منتهية، توقيع غير صالح، إيقاف حساب، طلب بلا صلاحية، وتعطل API أثناء الحفظ.
سلّم runbook لتدوير الاعتماد لدى المالك دون طباعته. إذا تعذر تأكيد الإبطال الخارجي، علّم البند blocked ولا تعتبر بوابة الأمان مكتملة.

حدود هذه المهمة:
- نفذ هذه الخطوة وحدها ثم توقف وسلّم تقريرها؛ لا تنتقل تلقائياً إلى الخطوة التالية.
- اعتمد على حالة الكود والاختبارات الحالية؛ نتائج المراجعة السابقة إشارات للتحقق وليست نتائج مضمونة اليوم.
- لا تعتبر غياب ملف تقرير سابق دليلاً وحيداً على نقص التنفيذ؛ تحقق من الأدلة والعقود واختبارات القبول.
- فحص وجود الأسرار يكون دون عرض قيمها؛ لا تكررها في diff أو السجلات أو التقرير. افصل نجاح إصلاح الكود عن تأكيد تدوير الاعتماد الخارجي.

في نهاية الرد حدد: مكتمل / جزئي / blocked، مع أدلة كل معيار قبول والمخاطر المتبقية.
```
