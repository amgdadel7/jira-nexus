# برومبتات AI Agent لكل خطوة تنفيذ

تاريخ: 20 أكتوبر 2026. المرجع: [خطة التنفيذ](COMPETITIVE_EXECUTION_PLAN_AR.md).

## طريقة التشغيل

ميزة اختيار أسلوب العمل: [المواصفة](WORK_MANAGEMENT_METHODS_AR.md) و[البرومبت المستقل](prompts/methodology_selection.md)، موزعة على 10A و12A و14A–15A و23A.

كل برومبت أدناه جاهز للاستخدام **بدمجه مع العقد العام التالي**. انسخ العقد ثم خطوة واحدة. لا تطلب تنفيذ 28 خطوة دفعة واحدة. البرومبتات تعليمات عمل مستقبلية وليست سجلاً لتنفيذ حدث بالفعل.

## العقد العام الإلزامي — يسبق كل خطوة

```text
أنت وكيل هندسة منتج يعمل على مستودع jira-nexus الحالي. نفذ الخطوة المحددة بعد هذا العقد فقط.

السياق:
- اقرأ AI_DEVELOPMENT_RULES.md وdocs/SYSTEM_REVIEW_AR_2026-10-20.md وخطة التنفيذ وبرومبت الخطوة.
- افحص git status والتغييرات الموجودة. لا تمسح عمل المستخدم ولا تستبدل قاعدة بياناته ولا تعيد seed لها.
- اعمل على الفرع المرتبط بالجلسة الحالية فقط، وتحقق منه بتعليمات الجلسة وgit branch --show-current؛ لا تنشئ أو تبدل فروعاً، ولا commit/push/PR إلا بطلب. لا تستخدم اسم فرع من جلسة سابقة.
- لا تفترض أن README يصف التشغيل الحالي. تتبع package scripts ونقطة الدخول والواجهة وقاعدة البيانات وملفات النشر.
- تحقق من اعتماديات الخطوة في الخطة. إذا لم تتحقق، وضح العائق وتوقف عن التغييرات المعتمدة عليها؛ لا تصطنع اكتمالها.

قبل التنفيذ:
1. اعرض جرداً مختصراً: الموجود، الجزئي، الناقص، والأدلة بمسارات الملفات.
2. اعرض النطاق والملفات والعقود وترحيلات البيانات والمخاطر وخطة الاختبار والتراجع.
3. قسّم المهمة الكبيرة إلى أجزاء قابلة للمراجعة. لا تدّعِ تنفيذ أجزاء لم تنجزها.

ضوابط التنفيذ:
- أعد استخدام الوحدات الصحيحة؛ لا تنشئ مساراً موازياً أو framework جديداً أو تعيد كتابة التطبيق دون ADR مبرر.
- التزم بوحدات المجال وفصل HTTP عن قواعد العمل والتخزين. أضف DTO والتحقق من المدخلات وأخطاء واضحة.
- تحقق من الهوية والمستأجر والصلاحية على الخادم لكل مورد وعملية، بما فيها البحث والملفات وjobs والأحداث والتصدير.
- لا تستخدم نجاحاً وهمياً عند فشل API، ولا mock إنتاجياً، ولا secret أو بيانات شخصية في السجلات.
- لا تقرأ أو تطبع أو تنسخ أسراراً في الرد. استخدم placeholders في الأمثلة، ومتغيرات بيئة ومخزن أسرار.
- لا تنفذ تدوير اعتماد خارجي أو ترحيل إنتاج أو حذف تاريخ Git أو نشر أو اتصالاً مدفوعاً دون تفويض منفصل.
- migrations مرقمة مع اختبار من قاعدة جديدة ومن الحالة السابقة؛ اختبر على بيانات اصطناعية أو نسخة مأذونة ومعزولة.
- للعمليات الحساسة عالج التزامن وidempotency وحدود الاستخدام. لا تعد بـexactly-once عبر أنظمة خارجية.
- واجهات جديدة قابلة للترجمة وRTL والوصول، مع loading/empty/error/retry. احترم عقود الميزات القديمة المعتمدة.
- اكتب اختبارات happy/failure/edge cases والصلاحيات والعزل عند انطباقها؛ لا تحذف اختباراً فاشلاً أو تضعف تأكيداته لتمريره دون تفسير تغيير العقد.
- عند تشغيل preview اربط 0.0.0.0 واستخدم /api نسبيّاً مع proxy؛ لا تجعل متصفح المستخدم يتصل بـlocalhost لخادم آخر.

التسليم:
- ملخص التغييرات والملفات، أوامر التحقق ونتائجها الفعلية، وأي اختبار لم يعمل وسببه.
- تحديث docs/execution/step-NN.md: معايير القبول كل منها pass/fail/blocked ودليله، القرارات، المخاطر، الترحيل والتراجع والخطوة التالية.
- اعرض git diff --check وراجع الفرق بحثاً عن الأسرار والتغييرات غير المقصودة.
- لا تقل «جاهز للإنتاج» أو «متوافق بالكامل» أو «آمن تماماً» اعتماداً على نجاح البناء وحده.
```

## 01 — معالجة موانع الأمان العاجلة

```text
نفذ الخطوة 01: تأمين الوضع الحالي قبل التوسع.
افحص render.yaml ومسار api/index.js → app.js → auth.js والصلاحيات في web/src/api.js، وتحقق من المسار الجديد أيضاً.
أزل الأسرار الصريحة من ملفات الإعداد لصالح مراجع آمنة، وأضف مثال إعداد بلا قيم حقيقية وفحص أسرار لا يعرض القيم. لا تغيّر تاريخ Git أو تستخدم بيانات الاتصال.
أزل fallback الذي يربط مستخدماً مفقوداً بهوية أخرى، وأوقف قبول جلسة ملغاة بإعادة إنشائها من التوقيع. امنع الأسرار الافتراضية في الإنتاج، مع فشل إقلاع واضح.
اجعل فشل حفظ/قراءة الصلاحيات ظاهراً وآمناً بدلاً من اختلاق نجاح أو صلاحيات واسعة.
اختبر: مستخدم غير موجود، جلسة ملغاة/منتهية، توقيع غير صالح، إيقاف حساب، طلب بلا صلاحية، وتعطل API أثناء الحفظ.
سلّم runbook لتدوير الاعتماد لدى المالك دون طباعته. إذا تعذر تأكيد الإبطال الخارجي، علّم البند blocked ولا تعتبر بوابة الأمان مكتملة.
```

```text
القبول: smoke test يبدأ نقطة الدخول المعتمدة، يسجل الدخول، ينشئ ويقرأ مورداً، ويعمل عبر proxy. صنف المسارات الأخرى legacy ولا تحذفها قبل تحقق التوافق.
```

## 03 — ترحيل البيانات والمحافظة على التوافق

```text
نفذ الخطوة 03 بعد اعتماد 02. قارن SQLite والمخططات القديمة بمخطط PostgreSQL المعتمد؛ افحص العلاقات والمعرفات والملفات والحالات والحقول والجلسات.
ابنِ أداة ترحيل versioned بـdry-run وتقرير mapping وعدد الكيانات والأيتام والتعارضات. استخدم fixtures لا قواعد البيانات الحقيقية المتتبعة. لا تعِد seed فوق بيانات موجودة.
حدد سياسة الجلسات: لا تنقل رموزاً غير آمنة كجلسات صالحة؛ فضّل إعادة تسجيل دخول موثقة عند تغيير نموذج الأمان.
عالج التكرارات والتواريخ والمناطق الزمنية والملفات والمعرفات بمخرجات معلنة، مع checkpoint أو إعادة تشغيل آمنة.
اختبر من قاعدة جديدة ومن نسخة سابقة وبيانات غير مكتملة وفشل منتصف الترحيل، وأثبت مطابقة العلاقات والأعداد والاستعادة.
القبول: لا فقد صامت، تقرير استثناءات مفهوم، وخطة cutover/rollback مجربة في بيئة معزولة. لا تنفذ cutover إنتاجياً دون تفويض.
```

## 05 — تشغيل وملفات واستعادة موثوقة

```text
نفذ الخطوة 05 بعد 03 و04. ثبّت Docker/config ومسار التخزين الدائم وقاعدة الإنتاج وhealth/readiness وإيقافاً آمناً للخادم.
أنشئ واجهة تخزين ملفات مع تحقق نوع/حجم وصلاحية تنزيل؛ تجنب رموز الجلسة في URLs، واستخدم روابط قصيرة العمر أو طلباً مصادقاً. أضف سياسة فحص ملفات وحجر إن تطلب النطاق.
أضف سجلات منظمة بـrequest ID ومقاييس أساسية دون بيانات حساسة؛ راجع مزودي الرصد الحاليين وما يرسلونه.
اكتب وشغّل تمرين backup/restore على بيئة معزولة يشمل DB والملفات، وحدد RPO/RTO كأهداف لا نتائج مفترضة.
القبول: إعادة نشر لا تفقد البيانات، ملف غير مصرح يرفض، readiness يكشف تعطل DB، والاستعادة مثبتة بتقرير توقيت واتساق. لا تشترِ خدمة أو تنشر إنتاجياً دون إذن.
```

## 06 — المؤسسات ومساحات العمل وعزل العملاء

```text
نفذ الخطوة 06 بعد 03–05. صمم organizations/workspaces/memberships وسياسة امتلاك الموارد، بترحيل واضح للموجود إلى مؤسسة افتراضية لا تخلط العملاء.
استخرج tenant من جلسة وعضوية موثوقتين، وتحقق من كل معرف مورد؛ لا تثق بـheader وحده. طبّق العزل على الاستعلامات والقيود الفريدة والعلاقات والتخزين والبحث والتقارير وcache/events/jobs.
إذا استخدمت PostgreSQL RLS، اختبر دور التطبيق الحقيقي وتسرب tenant عبر connection pool؛ لا تعتبر RLS بديلاً عن قواعد المجال.
اختبر مستخدماً متعدد المؤسسات، تغيير المساحة، معرفات متقاطعة، تصديراً، SSE وملفات ووظائف خلفية.
القبول: مجموعة اختبارات cross-tenant سلبية شاملة ومصفوفة موارد وعزل، وعدم كشف وجود المورد المحظور عبر محتوى الخطأ.
```

```text
أضف إدارة جلسات وأجهزة وإبطال فعلي، وMFA بـTOTP باستخدام مكتبة موثوقة وتشفير الأسرار وأكواد استعادة مجزأة وتأكيد حديث للأفعال الحساسة. قيّم WebAuthn كجزء لاحق إذا كبر النطاق.
احمِ التسجيل والتعطيل والاسترجاع من brute force وenumeration؛ لا تجعل recovery مسار تجاوز للمصادقة.
اختبر عاملين متزامنين، إعادة استخدام رمز، استرجاع، تغيير دور، مغادرة مساحة، وتعطيل حساب وجلساته.
القبول: مصفوفة roles/actions/resources واختبارات مستقلة لها، وسحب الصلاحية يسري على العمليات والملفات والمهام الجديدة.
```

## 08 — SSO وSCIM وتدقيق وسياسات بيانات

```text
نفذ الخطوة 08 بعد 07، وقسمها إلى هوية ثم حوكمة إذا لزم. أضف OIDC/SAML مؤسسياً عبر مكتبات موثوقة وموفر اختبار، ولا تكتب بروتوكول تحقق خاصاً.
اربط provider بالمؤسسة، مع تحقق issuer/audience/state/nonce/signature حسب البروتوكول؛ لا تربط هوية اعتماداً على بريد غير موثق. حافظ على break-glass مضبوط ومدقق.

أضف سجل تدقيق منظماً وسياسات احتفاظ/تصدير/حذف تحفظ المراجع ولا تعرض الأسرار؛ أعلن حدود عدم قابلية التعديل.
القبول: اختبار دخول مؤسستين ومنع خلط الهويات وإعادة الرسائل، وتعطيل موظف يسحب الوصول. وثق متطلبات الامتثال كعمل قانوني/تشغيلي ولا تدّعِ شهادة.
```

## 09 — أحداث وطوابير وتحديثات متعددة النسخ

```text
نفذ الخطوة 09 بعد 05–07. صمم outbox في المعاملة نفسها مع تعديل المورد، وعاملاً للمهام الدائمة بـretry/backoff/dead-letter وحدود tenant ومفاتيح idempotency.
وحّد envelope للأحداث بإصدار وactor/tenant/correlation دون أسرار. راجع SSE/presence عند عدة نسخ ومحددات المحاولات؛ اختر Redis أو بديلاً فقط عند تبرير الحاجة.
حدد ترتيب الأحداث وحدود الضمان: at-least-once مع مستهلك يتحمل التكرار، لا وعد exactly-once.
اختبر انقطاع العامل بعد الأثر وقبل acknowledgement، رسائل قديمة، تكرار، تعطل وسيط، سحب صلاحيات قبل تنفيذ job وتسرب بث لمؤسسة أخرى.
القبول: عدم تكرار الأثر التجاري، أدوات إعادة محاولة آمنة، ومقاييس backlog والفشل والمهام المعزولة.
```

## 12 — مساحات حسب الدور وقوالب وتهيئة

```text
نفذ الخطوة 12 بعد 07 و10 و11. صمم onboarding يختار نوع الفريق، ثم يطبق template بإصدار قابل للتعديل دون فرض نسخة بيانات منفصلة.
```
