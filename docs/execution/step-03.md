# تقرير تنفيذ الخطوة 03: ترحيل البيانات والمحافظة على التوافق

## 1. ملخص تنفيذي
تم في هذه الخطوة بناء واختبار أداة ترحيل بيانات احترافية وقابلة للإصدار (`versioned`) لنقل البيانات من مخطط SQLite القديم إلى مخطط PostgreSQL المعتمد، دون المساس بقاعدة البيانات الحية للمستخدم أو إعادة تهيئتها (`seed`). شملت الأداة دعماً كاملاً للفحص الجاف (`--dry-run`)، ومطابقة العلاقات والأنواع المتباينة (مثل حقول JSONB، والتسميات، والمكونات، وسلاسل الهوية)، واكتشاف الأيتام ومعالجتها مع تقرير استثناءات صريح، وتطبيق سياسة أمنية صارمة بعدم ترحيل الجلسات القديمة غير الآمنة مع فرض إعادة تسجيل الدخول الموثقة. تم اختبار عمليات الترحيل في بيئات معزولة (PGlite In-Memory) بنجاح 100% عبر 6 اختبارات متخصصة، ليصل إجمالي اختبارات النظام إلى 48 اختباراً دون أي إخفاق.

## 4. القرارات الهندسية والمعمارية (Key Architectural Decisions)

1. **إبطال الجلسات القديمة وفرض إعادة تسجيل الدخول (Session Invalidation Policy)**:
   - تم اتخاذ قرار حازم بعدم ترحيل رموز الجلسات القديمة المخزنة في SQLite، نظراً لتغيير النموذج الأمني واعتماد توقيع HMAC والتحقق الصارم من صحة الجلسات. يضمن هذا الإجراء عدم تسرب أي جلسات قديمة غير موثقة إلى البيئة المحدثة.
2. **عزل المعاملات الذرية (Atomic Transactional Migration)**:
   - تم تغليف عملية الترحيل بالكامل داخل `db.tx()`، بحيث يؤدي أي خطأ طارئ في منتصف الترحيل إلى تراجع تلقائي (`ROLLBACK`) دون ترك قاعدة البيانات الهدف في حالة غير متسقة أو مشوهة.
3. **معالجة التعارضات الصريحة (Explicit Conflict Resolution)**:
   - إذا تضمنت بيانات المصدر سبرنتين نشطين لنفس المشروع (وهو ما تمنعه قيود PostgreSQL الفريدة المشروطة `WHERE state = 'active'`)، تقوم الأداة بإبقاء السبرنت الأحدث نشطاً وخفض السبرنت الآخر إلى `future` مع تسجيل ذلك صراحة في التقرير.
   - في حال وجود مهام تشير إلى مستخدمين محذوفين في `assignee_id` أو `reporter_id`، يتم ضبط الحقل إلى `NULL` تفادياً لكسر قيود التكامل المرجعي مع تسجيل الحالة كيتيم معالج.
4. **تحديث سلاسل الترقيم (Identity Sequences Auto-sync)**:
   - نظراً لأن جداول PostgreSQL تستخدم `GENERATED BY DEFAULT AS IDENTITY`، تم تضمين خطوة نهائية لتنفيذ `setval(..., MAX(id))` لكافة الجداول لضمان جاهزية النظام الفورية لاستقبال إدخالات جديدة دون تعارض في المفاتيح الأساسية.

## 5. خطة الانتقال والتراجع (Cutover & Rollback Plan)

> [!IMPORTANT]
> **تنبيه حرج**: لا يتم تنفيذ خطة الترحيل على بيئة الإنتاج الحية إلا بعد صدور تفويض كتابي منفصل من إدارة النظام.

### إجراءات الانتقال المعزول والمختبر (Verified Cutover Procedure):
1. **أخذ نسخة احتياطية فورية وقفل القراءة/الكتابة**:
   - إيقاف خدمة SQLite القديمة أو وضعها في وضع القراءة فقط (`db.pragma('query_only = ON')`).
   - نسخ احتياطي للملف: `cp api/data/jira.db api/data/jira.db.bak.$(date +%F_%T)`.
2. **تشغيل الفحص الجاف أولاً**:
   - تنفيذ `npm run db:migrate-data -- --dry-run --report-json migration-preflight.json`.
   - مراجعة تقرير الأيتام والتعارضات والتأكد من مطابقة الأعداد.
3. **تنفيذ الترحيل الفعلي**:
   - تنفيذ `npm run db:migrate-data -- --source api/data/jira.db --report-json migration-final.json`.
4. **التحقق من صحة النظام بعد الترحيل**:
   - تشغيل `npm run health` للتحقق من سلامة الواجهة الخلفية وقاعدة البيانات.
   - تشغيل `npm run test:smoke` للتحقق من قدرة النظام على المصادقة وإنشاء وقراءة المهام.

### خطة التراجع (Rollback Procedure):
1. في حال حدوث أي طارئ غير متوقع أو عدم مطابقة في الأعداد، يتم إيقاف خادم PostgreSQL.
2. إعادة تشغيل الواجهة الخلفية القديمة بالاعتماد على SQLite عبر الأمر:
   `npm run start:legacy`
3. إعادة توجيه reverse proxy أو منفذ التطبيق إلى المنفذ `8080`.
4. تعود كافة العمليات للعمل فوراً على نسخة SQLite الأصلية دون فقدان أي بيانات، نظراً لكون عملية الترحيل لم تعدل بتاتاً ملف المصدر.
