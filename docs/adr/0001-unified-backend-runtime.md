# ADR 0001: اعتماد مسار تشغيل موحد للواجهة الخلفية وقاعدة البيانات

- **الحالة**: معتمد (Accepted)
- **التاريخ**: 2026-10-20
- **السياق**: وجود تشتت وتعدد في مسارات التشغيل داخل المستودع (Node.js Legacy SQLite Monolith مقابل Node.js Clean Architecture PostgreSQL مقابل .NET 8 Web API).

---

## 1. سياق القرار والمشكلة (Context & Problem Statement)
يحتوي المستودع على ثلاثة مسارات تشغيل غير متجانسة:
1. **مسار Node.js القديم (`api/index.js` → `app.js`)**: يعمل فوق SQLite (`better-sqlite3`) بنمط Monolithic Route Handlers مباشر.
2. **مسار Node.js الحديث المعماري (`api/src/main.js`)**: يطبق Clean Architecture مع فصل الطبقات (Domain, Application, Infrastructure, Presentation, Interfaces) ويعتمد PostgreSQL مع محرك PGlite المدمج للاختبار والتطوير المحلي.
3. **مسار .NET 8 (`backend/src/Masar.Api`)**: تطبيق C# ASP.NET Core Clean Architecture جزئي غير مكتمل الميزات.

تسبب هذا التشتت في تضارب إعدادات Vite، وتوجيه النشر السحابي في Render لخدمات غير متوافقة، وازدواجية ملفات التهيئة (`client/dist` مقابل `web/dist`)، وفقدان مسار موحد لاختبارات CI/CD والتشغيل المحلي.

---

## 2. تقييم ومقارنة الخيارات (Options Comparison)

| معيار المقارنة | الخيار 1: Node.js (`src/main.js`) + PostgreSQL | الخيار 2: Node.js Legacy (`app.js`) + SQLite | الخيار 3: .NET 8 (`Masar.Api`) + PostgreSQL |
| :--- | :---: | :---: | :---: |
| **اكتمال ميزات المجال (Domain Completeness)** | **100%** (جميع الميزات: JQL، الحسابات، السبرنتات، SSE، المهام المؤتمتة، خطط الصلاحيات، الفواتير) | **100%** | **~30%** (ناقص: محرك JQL، تقارير Velocity/CFD، البث الحي SSE، تتبع الوقت، Webhooks Redelivery) |
| **التوافق مع AI_DEVELOPMENT_RULES** | **متوافق تماماً** (Clean Architecture + PostgreSQL + DTOs + Repository) | غير متوافق (Monolith + SQLite) | متوافق معمارياً لكن غير مكتمل الميزات |
| **قابلية التوسع الأفقي (Horizontal Scalability)** | **عالية** (قاعدة بيانات PostgreSQL منفصلة، دعم Connection Pooling) | منعدمة (ملف SQLite محلي يقفل عند تعدد الحاويات) | عالية |
| **الترحيلات الآلية (Migrations)** | **جاهزة** (9 ترحيلات SQL مرقمة ومختبرة من `001` إلى `009`) | غير مرقمة (seed أحادي) | ترحيلات EF Core جزئية |
| **تكلفة الانتقال والمخاطر (Transition Cost)** | **منخفضة** (المسار مبني بالفعل ويجتاز 42 اختباراً، يتطلب فقط نقل بيانات SQLite في خطوة 03) | صفرية فورية لكن دين تقني مرتفع جداً | **مرتفعة جداً** (تتطلب شهوراً لإعادة بناء محرك JQL والتقارير في C#) |

---

## 3. القرار المعتمد (Decision Outcome)
1. **اعتماد `Node.js (api/src/main.js) + PostgreSQL` كمسار تشغيل وإنتاج وحيد ومعتمد** للمنظومة.
2. **تصنيف المسارات الأخرى كمسارات قديمة/مرجعية (Legacy / Reference)** وعدم حذفها فوراً منعاً لأي فقدان للكود حتى استكمال نقل البيانات والتحقق التام:
   - مسار SQLite القديم متاح تحت الأمر `npm run start:legacy`.
   - مسار .NET 8 يُحتفظ به في مجلد `backend/` كمرجع دون ربطه بـ Render أو الحاوية النشطة.
3. **توحيد أوامر البدء والفحص والحاويات والـ Proxy**:
   - `npm start` يشغل `api/src/main.js` على المنفذ `3000`.
   - `npm run health` يستعلم عن `/api/health` من المسار المعتمد.
   - Vite في `web/` يوجه طلبات `/api` إلى المسار المعتمد عبر proxy داخلي نسبي.
4. **تثبيت اعتماد نقل البيانات للخطوة 03**: لن يتم تحويل أي قاعدة بيانات إنتاجية أو شطب ملف `jira.db` قبل تنفيذ واعتماد سكربت ترحيل البيانات المفصل في الخطوة 03.

## 5. النتائج والآثار (Consequences)
- **الإيجابيات**:
  - وجود نقطة انطلاق موحدة خالية من التشتت لجميع المهندسين وأدوات CI/CD.
  - إنهاء تضارب منافذ Vite والوجهات الثابتة (`web/dist` مقابل `client/dist`).
  - توفير بيئة تشغيل محلية سريعة وخفيفة بالاعتماد على PGlite دون إجبار المطور على تشغيل خادم Postgres ثقيل أثناء التطوير والاختبار.
- **القيود والتبعات**:
  - تبقى بيانات SQLite الحالية في بيئتها الأصلية حتى يتم نقلها بسلاسة وبأدوات موثوقة في الخطوة 03.
